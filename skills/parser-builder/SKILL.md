# Building a parser for one source

The result is one **source adapter**: a stdlib Python module with the contract in `leadgen/sources/__init__.py`.
The runner then caches it, throttles it, resumes it, merges its rows into leads and exports them, the same as the
bundled adapters. Follow the steps in order. Steps 1 and 2 decide whether there's anything to build.

Two homes:
- **Workspace** `<workspace>/leadgen_sources/<name>.py`: the default. One-off, personal, or niche sources. It is
  code from the workspace, so it loads **only** when the campaign's `campaign.toml` has `[[sources]] type = "<name>"`.
  `leadgen sources` lists it by name without running it.
- **Built in** `leadgen/sources/<name>.py`: only for sources useful to most users, and only via a PR with synthetic
  fixtures (step 4). Add the name to `MODULES`.

## 1. Qualify the source (go / no-go)

Write a short source card in the campaign's `brief.md` (or `reports/source-<name>.md`):

- **What a record gives**: name, website, phone, email, city, category, registry id, rating... Open 3 records.
  If no record has a website, phone or email, the source can't produce reachable leads. Say so before building.
- **Volume**: how many records match the campaign's ICP and geography? Count from the source's own totals.
- **Access**: is it reachable logged out? Captcha? Rate limits? Read `robots.txt` and the terms of use, and
  record what they say and the date.
- **Better routes**: an official API, open-data dump, CSV export or bulk download beats scraping. If one exists,
  use it (or the `file` adapter for a one-time export).

**Stop and tell the user** if the data sits behind a login, needs a captcha bypass, or the terms forbid automated
access. Offer the alternatives instead: an official export, the browser-assisted route in `lead-sourcing`
(a human-paced look via Playwright, findings recorded by hand), or a paid provider plugin. Don't build around a
wall.

## 2. Find the data path, cheapest first

Open the source in the Playwright MCP (`browser_navigate`, then `browser_network_requests`) and look in this order:

1. **Official API** (documented, maybe keyed). Pattern: `google_places.py`, `companies_house.py`.
2. **JSON the page itself calls** (XHR/fetch in the network log). Same data, stable shape, no HTML parsing.
   Check that the endpoint answers a plain GET/POST without session cookies. If it needs them, it's not usable.
3. **State JSON embedded in the HTML** (`__NEXT_DATA__`, `window.__INITIAL_STATE__`, `<script type="application/json">`,
   `"pagination":{...}`). Patterns: `yandex_maps.py`, `kwork.py`.
4. **Server-rendered HTML**: split on a per-record marker, then extract fields per block. Patterns: `flru.py`,
   `telegram.py`.
5. **External browser tool**: last resort, setup via `ready()` + a `leadgen setup` step. Pattern: `twogis.py`.

Confirm the path with a plain fetch, not just in the browser: `python3 -c` with `urllib.request`, using the
User-Agent the adapter will use. If the plain fetch lacks the data, that path won't work for the adapter.

Prefer stable identifiers (record ids, slugs) and structured attributes (`data-*`, `itemprop`, `href="tel:"`,
JSON keys) over visible text and CSS class names generated by a build tool.

See [references/patterns.md](references/patterns.md) for code for each pattern.

## 3. Units, pagination, stop rule

- **Unit** = one raw file, collected once and never refetched (unless `--refresh`). Usually `query × location`, or
  one category, or one whole feed. A unit should fit in a few minutes of polite fetching. Split big ones.
- **`unit_key`** must be stable for the same unit forever. That's what makes re-runs free.
- **Pagination**: page number, offset, cursor (`?before=<id>`), or a `next` token. Find the real "next" marker.
- **Stop rule**: no new ids on a page, total reached, no next marker, 404 past the end, or `max_pages`. Always cap
  with `max_pages` from the spec.
- **Live feeds** (orders, posts): `SNAPSHOT = True` and `ttl=20 * 3600` on fetches, so it re-collects daily.
- **Delay**: set in `fetcher(camp)`. 2 s is the default for HTML sites, 0.5–1 s for APIs that state their limits.
  Never lower it to go faster. Use more units over more runs instead.

## 4. Capture fixtures

- Save 2–3 real payloads to the scratchpad while developing: page 1, a middle page, and the last or empty page.
  Add a "no results" page if the source has one.
- For tests, **write synthetic fixtures**: the same markup or JSON shape, with invented businesses (`*.test`
  domains, `+000` phones). Real pages hold personal data and must not be committed. Workspace adapters keep
  fixtures next to them (`leadgen_sources/<name>_fixtures/`, which `leadgen init` gitignores). Built-in adapters keep
  them in `tests/fixtures/<name>/`.
- Trim fixtures to the parts the parser reads, so it's obvious what the parser depends on.

## 5. Write the adapter

Start from `${CLAUDE_PLUGIN_ROOT}/templates/source.py` and replace every TODO. Rules:

- **`parse()` is pure** (payload in, rows out, no I/O). `collect_unit()` fetches and paginates. Tests depend on this split.
- **Fail loudly.** Raise `LayoutChanged` (from `leadgen.sources`) when the structure you rely on is missing.
  Raise `Blocked` (from `leadgen.core.http`) on captcha, 429 or access walls. Return `[]` only for a page that is
  valid and empty. A parser that returns 0 rows after a redesign is the worst failure: it looks like an empty market.
- **Rows use the merge field names**: `source_id, url, name, sites[], phones[], emails[], city, country, address,
  lat, lon, categories[], segment, rating, reviews, legal{name, registry_ids}, signals[]`, social keys
  (`linkedin, instagram, telegram, whatsapp, vk, ...`). Demand rows: `title, description, budget, budget_max,
  currency, category, offers, created, type`. `url` is the record's own page on the source, and it is the
  evidence link for every fact from this source.
- Lists stay lists (a record with two phones gives `phones: [a, b]`). Leave a field `None`/`[]` when absent. Never
  fill it in with a guess.
- **All network access goes through `ctx.fetcher`** (cache, throttle, `Blocked` detection). API keys go in headers,
  never in the URL (the URL is the cache key and gets logged). Read keys from `os.environ`, listed in `ENV`.
- Docstring: data path and why, pagination and stop rule, ToS/robots check with its date, spec keys with an example.

## 6. Test offline

Workspace adapters: a small `unittest` file next to the adapter. Built in: `tests/test_<name>.py`. Cover:

- `parse()` on each fixture → the exact expected rows (names, ids, sites, phones).
- `parse()` on a redesigned or empty page → `LayoutChanged`; on a captcha page → `Blocked`; on "no results" → `[]`.
- `collect_unit()` with `tests.fakes.FakeFetcher` (routes keyed by URL) walks the pages and stops by the stop rule.
- `units()` / `unit_key()` are stable, and keys are file-safe.
- Rows survive `leadgen.core.merge.normalize` (it keeps the site, normalizes phones, gives a stable id).

`tests/test_sources.py::test_template_is_a_working_adapter` shows the whole pattern in 15 lines.

## 7. Live check, small

```sh
leadgen sources                                # the adapter shows up (workspace path printed)
leadgen collect <slug> --source <name>         # set max_pages = 1 and one query/location first
leadgen inspect <slug> --source <name>         # rows, fill rate per field, sample rows, duplicate ids
```

- Open 3 sample rows' `url` in the browser and compare field by field.
- Fill rates should match what you saw in step 1. A field at 0% that the page shows means the parser misses it.
  Many duplicate `source_id`s mean pagination is repeating pages.
- Then raise `max_pages` / add units, run `leadgen merge <slug>`, and check that leads from this source merge with
  the same businesses from other sources (`leadgen status`, `sources` column in the CSV).

## 8. Register and hand off

- **Workspace**: add the `[[sources]]` block to `campaign.toml` with a comment. Note the source card's go/no-go,
  ToS check date, and live-check date in `brief.md`'s decisions log.
- **Built in**: add to `MODULES`, add a commented `[[sources]]` example in `templates/campaign.toml`, a row in
  `docs/sources.md`, and the live-check date in `CURRENT_STATE.md`. All tests pass.
- Tell the user: what the source gives, how many records, fill rates, the delay used, and anything left manual.

## When an adapter breaks

`leadgen collect` prints `LAYOUT CHANGED` (the source stops after two units in a row) or a unit returns far fewer
rows than before. Re-capture one live payload, diff it against the fixture, update the fixture first (the test
should now fail), fix `parse()`, rerun the tests, then `leadgen collect --refresh --source <name>` for the units
collected during the breakage.
